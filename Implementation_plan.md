# Implementation Plan - SportsHuddle

SportsHuddle is a weekly package of Premier League data (Dashboard PDF, Excel Data, Cheat Sheet) distributed via Email/WhatsApp, centered around a high-converting one-page website.

## User Review Required

> [!IMPORTANT]
> **Data Source Strategy**: I plan to start by looking for reliable free/freemium APIs (e.g., API-Football, football-data.org) or public CSV repositories (e.g., football-data.co.uk). Please confirm if you have a preferred source or existing data dump.

> [!WARNING]
> **Distribution Costs**: WhatsApp Business API (via Twilio/Meta) usually has per-conversation costs. Email (SendGrid/Mailgun) has free tiers but scales with volume. We will implement the *collection* of contacts first, but the actual *sending* logic will require API keys and potentially credit card setup on your end later.

> [!NOTE]
> **Hosting**: For the one-page site, I recommend Vercel or Netlify (Free Tier).

## Proposed Tech Stack

- **Frontend (Hosting: Vercel)**: React + Vite
  - Fast, responsive static site served from Vercel's global CDN.
  - **Styling**: Vanilla CSS (CSS Modules) for premium aesthetics.
  - **State**: React Hook Form for signups.

- **Backend Logic & Database (Supabase)**:
  - **Database**: PostgreSQL (managed by Supabase).
  - **Storage**: Buckets for storing the generated PDF dashboards and Excel sheets.
  - **Auth/Signups**: Supabase Auth (Phone/Email).

- **Data Processing & Report Generation (Python)**
  - *Challenge*: Vercel Serverless functions have timeout limits (10-60s) which might be too short for generating heavy PDFs or fetching large datasets.
  - *Solution*: **GitHub Actions (Scheduled Cron)** or Local Script.
    - We will use a Python script running on a schedule (e.g., every Monday) to:
      1. Fetch Data.
      2. Generates PDF/Excel with `pandas` and `fpdf2`/`reportlab`.
      3. **Uploads** files to Supabase Storage.
      4. **Inserts** match data into Supabase DB.
      5. Triggers the distribution logic.
  - *Can we use Python on Vercel?* Yes, for simple APIs (like "get latest stats"), but for the heavy "Weekly Generate" task, a long-running script (GitHub Action) is superior and free.

## Data Schema (Supabase / SQL)

```sql
-- USERS: People signed up for the newsletter
create table users (
  id uuid references auth.users primary key,
  email text,
  phone text,
  preferences jsonb, -- e.g. { "team": "Arsenal", "format": "whatsapp" }
  created_at timestamp with time zone default now()
);

-- MATCHWEEKS: Tracking each week's generation
create table matchweeks (
  id bigint generated by default as identity primary key,
  season text, -- "2024-2025"
  week_number int,
  pdf_url text, -- Link to Supabase Storage
  excel_url text,
  published_at timestamp with time zone
);

-- MATCHES: Core data for the web dashboard preview
create table matches (
  id bigint generated by default as identity primary key,
  matchweek_id bigint references matchweeks,
  home_team text,
  away_team text,
  home_score int,
  away_score int,
  metrics jsonb -- { "xG": 1.2, "possession": 45 }
);
```

## Distribution & Integrations

Supabase isn't an email/SMS *provider* itself (it wraps providers for Auth), but we can integrate easily:
- **Email**: SendGrid or Resend API.
- **WhatsApp**: Twilio API or Meta Business Cloud API.
- **Orchestration**:
  - The **Python Script** can call these APIs directly after generating the files.
  - OR use **Supabase Edge Functions** (TypeScript) triggered by a database web hook when a new `matchweek` is inserted.
  - *Recommendation*: Keep it simple first. Have the Python script send the messages immediately after generating the reports.

## Verification Plan

### Automated Tests
- **Data Validation**: specialized script to check if fetched PL data is not empty and contains expected columns.
- **Generation Check**: script to assert output files (`dashboard.pdf`, `data.xlsx`) exist and are non-zero size after running `main.py`.

### Manual Verification
- **Visual Check**: Open generated PDF to verify layout and data accuracy.
- **Website**: Open `localhost:3000` to verify responsiveness, animations, and signup form console logs (simulating submission).
